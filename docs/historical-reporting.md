# Historical reporting populations

ITQAN reports separate viewer authorization from report population.

- Authorization is current: a normal admin sees history only for masajid they actively administer on `current_toronto_civil_date()`. A super admin sees all report scopes. A student must be signed in through an active student profile and sees only a cohort they belonged to in the selected week.
- Population is historical: every canonical Sunday is resolved independently from `student_group_memberships.starts_on <= week_start` and a null or inclusive `ends_on >= week_start`. Later profile role/activity and hierarchy activity do not remove the row.
- Scoring eligibility is separate: `profiles.score_starts_on` must be non-null and no later than the report week. Population absence and scoring ineligibility produce no score row; an eligible row with no activity keeps the existing zero/missing score behavior.
- Contact projection is current: historical-only admins receive the current display name and metrics, but null phone/email and false profile-link flags unless the student is also in an active current student scope administered by that viewer. Super admins retain global visibility.
- Placement comes only from historical membership: its masjid, cohort, and group control report grouping, labels, authorization, and population. Activity snapshots never move the report row.
- Points use a separate attribution rule. Exact-scope activity counts. A same-student/week activity row with the membership masjid but a different stored cohort or group also counts and remains an integrity finding. An explicit cross-masjid snapshot is excluded. A legacy null-masjid row counts only when exactly one effective membership makes attribution unambiguous. No or ambiguous membership excludes the activity and the report row.
- Application report loaders obtain score fields through `historical_reporting_activity_for_weeks(date[])`. This security-definer projection applies current viewer authorization and historical attribution before returning sanitized score inputs; raw activity-table RLS remains strict and is not weakened for legacy rows.
- Exact masjid/cohort/group equality remains mandatory for new or edited grades, pending obligations, and other integrity/write boundaries. Report compatibility does not weaken teacher grading or obligation scope authorization.

`historical_reporting_students_for_weeks(date[])` validates Sundays, deduplicates inputs, enforces current caller scope, and returns deterministic ordering. Application loaders page the batch result and activity queries beyond the Data API row cap, while chunking student filters. Operational current-roster loaders remain separate.

Selectable weeks are deliberately evidence-bounded. `historical_reporting_available_weeks()` takes the distinct canonical Sunday scopes represented by check-ins, partner recitations, halaqa grades, accountability obligations, badge awards, and completed weekly incentive runs, plus the current tracker week for the live leaderboard. It then intersects those candidates with an effective membership and `score_starts_on`, and excludes every week after the current tracker week. This retains intentional zero/missing rows for eligible peers in a report-bearing scope without expanding a membership interval into empty Sundays. In particular, the `1900-01-01` legacy membership sentinel is identity history, not a reporting-calendar floor. `score_starts_on` is an eligibility intersection, not the sole source of available weeks.

Student leaderboard scope and peer RPCs enforce that same bounded rule inside PostgreSQL: the caller must be a currently active student, historically and scoring eligible in the requested cohort/week, and the week must be evidence-backed for that exact historical cohort or be the current tracker week. PostgreSQL and the application both use the established 1:00 a.m. Toronto tracker-day boundary (`current_effective_date()` / `checkInEffectiveDateString()`), so a scheduled Sunday transfer remains future through Sunday 00:59. A future Sunday is never allowed, even if a transfer and report evidence have already been scheduled. The page loads this database allowlist first; a rejected `?week=` value falls back to the current week when allowed, otherwise to the latest allowed historical week, and is never echoed into the dropdown or used for scope, teacher, or peer queries.

Previous ranks preserve the established activity gate: if nobody in the caller's previous historical cohort has attributable report activity, no previous ranks are returned. Once that leaderboard has activity, an eligible peer with no individual activity retains the normal zero-score rank. Joining or beginning official scoring in the selected week produces no previous rank.

Accountability reconciliation remains a server-only workflow. PostgreSQL recomputes the authoritative historical weekly percentage with the report-attribution rule, validates population and scoring eligibility, and atomically creates, refreshes, or auto-waives a pending row. New and pending rows still store the exact membership masjid/cohort/group; report attribution never relaxes that invariant. Paid and already-waived obligations are immutable and reconciliation returns without changing them. The Slice 4 database migration is a Phase A compatibility release: it keeps the deployed application's service-role direct insert, pending-update, and auto-waive contract, but validates its submitted score, amount, canonical completed week, student, and exact obligation scope against the same database computation. Existing authenticated-admin policies remain for rollout compatibility, but the trigger requires authoritative values on insert and makes identity, historical scope, score, and amount immutable on admin updates; browser permissions are not broadened. The new application uses the reconciliation RPC after deployment. Removing the legacy path or simplifying the trigger is a separate Phase C migration only after the new application is confirmed live.

Monthly badge leaderboards use the union of students scoring-eligible in at least one completed week belonging to the selected month. A displayed student's lifetime total is the sum of all computed badge awards from completed, historically eligible weeks visible in the caller's current reporting scope—not merely today's roster and not a global total outside that scope.

Historical names are not versioned in this slice. Reports display the currently stored profile, group, cohort, and masjid names for the historical IDs. Saturday-key weekly-plan remediation is also intentionally deferred.

`scripts/audit-historical-report-populations.sql` is read-only and uses the same bounded report-week evidence model. It keeps exact mismatch findings separate from scoring treatment and labels each activity mismatch as counted same-masjid placement, counted unambiguous legacy null-masjid, excluded cross-masjid, excluded missing-membership, or excluded ambiguous-membership. It compares existing scores with revised attribution scores, while continuing to report exact obligation-scope and settled-obligation findings. Its row-level output is identifier-only; no name, contact, note, or activity-content columns are selected, and it never rewrites source data.

`scripts/reconcile-historical-report-impact.sql` is the companion ID-only,
read-only impact packet. It reports component-level score deltas, threshold,
badge, incentive, streak and rank effects, source-row dispositions, and the
hypothetical outcome of settled-obligation anomalies without changing those
immutable rows.
